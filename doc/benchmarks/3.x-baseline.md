# 3.x 與 Dapper 的基準數字

v5 開工前（Phase 0 的 0.8）在 §10.2 各情境錄下的 3.x 與 Dapper 數字，作為 5.0 調校時的參考。

- **只供參考**：GitHub runner 每次分配到的硬體與負載都不同，這裡的時間不能拿來和之後的執行比較。§10.2 的放行條件一律以**同一次執行**裡一起量的比較對象為準（§10.2「怎麼比」）。
- **配置數量**不受機器影響，可以跨次比較；CI 每次都與 `src/Chef.DbAccess/Chef.DbAccess.Benchmarks/allocation-baseline.json` 比對（§10.3）。
- 下表的「比值」是在**同一個執行環境內**與比較對象相比（BulkInsert 是 SqlBulkCopy，其餘是 Dapper）。BenchmarkDotNet 報表上的 Ratio 欄是拿 .NET Framework 4.8 的數字去比 .NET 10 的 Dapper，不能直接用來判斷。

寫法的名稱與基準專案的方法名稱相同：

- `Dapper`：Dapper 執行手寫的等價 SQL。
- `Chef3x`：3.x 的 LINQ 寫法。
- `Chef3xRawSql`：3.x 的 Raw SQL 寫法。
- `HandWritten`：手寫的強型別讀取。
- `SqlBulkCopy`：直接使用 `SqlBulkCopy`。

## 觀察

- **3.x 的開銷在 LINQ 翻譯，不在執行**：
  - `Chef3xRawSql` 在所有情境都與 Dapper 相當，時間 0.94～1.10 倍，配置 1.01～1.06 倍。3.x 的 Raw SQL 就是 Dapper，差異在量測雜訊之內。
  - `Chef3x` 每次查詢多出固定的時間與配置。以 .NET 10 的主鍵查一筆為例，多了約 43 μs、16 KB。
  - 資料越多，翻譯成本佔的比例越小，所以查 1 萬筆時與 Dapper 幾乎相同。
- **離 5.0 的條件還很遠**：§10.2 要求「LINQ 一般寫法」比 Dapper 的額外時間 ≤ 2 µs、額外配置 ≤ 1 KB。3.x 在主鍵查一筆是 +43 µs／+16 KB，分頁是 +20 KB，三表 JOIN 是 +176 KB。
- **`Contains` 1,000 筆是最明顯的瓶頸**：
  - 3.x 把每個值翻成一個 OR 條件，.NET 10 慢 7.2 倍、配置 110 倍（約 81 MB）；.NET Framework 4.8 慢 16.7 倍。
  - 10 筆時也已經多配置 40 KB 左右。
- **.NET Framework 4.8 上 3.x 的開銷更大**：主鍵查一筆在 .NET 10 是 1.45 倍，在 .NET Framework 4.8 是 1.81 倍；`Contains` 1,000 筆從 7.2 倍變成 16.7 倍。5.0 的調校要兩種執行環境都量。
- **物件產生還有很大的空間**：手寫的強型別讀取在 .NET 10 只要 Dapper 15% 的時間、42% 的配置。§10.2 只要求「≤ Dapper」，5.0 的 Shaper 應該做得到。
- **BulkInsert**：3.x 的 TVP 在時間與配置上都大約是 `SqlBulkCopy` 的 2 倍。§10.2 要求 5.0「不慢於 3.x 的 TVP」，改用 `SqlBulkCopy` 可以留下充分的餘裕。

## 量測上的限制

- **寫入與小查詢的雜訊大約 ±10%**：
  - 新增一筆在 .NET 10 量到 `Chef3xRawSql` 1.10 倍，比做更多事的 `Chef3x` 的 1.01 倍還慢，只能是雜訊。
  - 主鍵查一筆的 `Chef3xRawSql` 是 1.09 倍，標準差約 5%。
  - §10.2 的 Raw SQL 條件「時間 ≤ Dapper × 1.03」比這個雜訊小，用預設的量測輪數可能分不出來。Phase 6 驗收 Raw SQL 前，要先決定增加量測輪數，或是改用其他判斷方式。
- **2 µs 的差異在資料庫情境裡量不出來**：分頁、JOIN、寫入每次約 1～2 ms，BenchmarkDotNet 的 Error 就有 20～50 µs。「LINQ 一般寫法：額外時間 ≤ 2 µs」需要不經過資料庫的情境才驗證得了，例如只量翻譯，或是使用假的 `DbDataReader`。
